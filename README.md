# Obsidian Quill

A global web novel and light novel platform: writers publish serialized fiction for free, and readers discover
stories through a fair, depth-based discovery system (the Fresh Shelf). Later stages add interactive choice-point
stories and AI-generated comic panels.

Stack: Next.js (App Router) + React + Tailwind CSS, Supabase (Postgres, Auth, Storage, Realtime, pg_cron), hosted on
Vercel.

## Getting started

1. Create a Supabase project.
2. Apply the schema: `supabase db push` (Supabase CLI, linked to your project), or paste
   `supabase/migrations/20261110000000_base_schema.sql` into the SQL editor.
3. In Supabase Auth, enable Email and Google providers, and add `http://localhost:3000/auth/callback` (plus your
   production URL) to the redirect allow list.
4. `cp .env.example .env.local` and fill in the project URL and anon key.
5. Enable the `pg_cron` extension (Database > Extensions) before applying the migrations, so scheduled chapters
   publish on time.
6. `npm install && npm run dev`, then open http://localhost:3000. `npm test` runs the unit tests.

## Deploying (Vercel + Supabase)

1. **Supabase.** In Database > Extensions, enable `pg_cron` and `pg_trgm`. Then run every file in
   `supabase/migrations/` in the SQL editor, oldest first (or `supabase link` and `supabase db push`). Migrations are
   only ever added, never edited after release, so run the new ones whenever you update.
2. **Auth.** Authentication > URL configuration: set the Site URL to your production address and add
   `https://YOUR-DOMAIN/auth/callback` to Redirect URLs. Enable the Google provider if you want Google sign-in.
3. **Vercel.** Import the repository and set these environment variables, then deploy:

   | Variable | Value |
   | --- | --- |
   | `NEXT_PUBLIC_SUPABASE_URL` | Project URL (Settings > API) |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Anon public key (Settings > API) |
   | `NEXT_PUBLIC_SITE_URL` | Your production address, e.g. `https://obsidianquill.vercel.app` (used for links, the sitemap and share cards) |
   | `OPENAI_API_KEY` | Optional. Without it, comic panels use the built-in demo artwork and cost nothing |
   | `OPENAI_IMAGE_MODEL` | Optional, defaults to `gpt-image-1` |

4. **Make yourself an admin.** Sign up on the live site, then in the SQL editor run
   `update public.profiles set is_admin = true where username = 'your_username';`. The account menu then shows
   Moderation (`/admin`): the report queue, takedowns and the stories featured for comic panels.
5. **Check:** `/robots.txt`, `/sitemap.xml` and a story's share card (`/story/<id>/opengraph-image`) should load.

Built-in limits (all enforced in the database): 10 comments per person per 5 minutes, 20 reports a day, 10 new
stories a day, 30 published chapters an hour, comic generations capped per chapter and at 60 per writer per day.

## Demo content (optional)

`supabase/seed/` holds 30 demo books (12 demo authors, 834 chapters across all 15 genres), three choice points and
a month of simulated reading activity, so the home rows, rankings and Fresh Shelf have something to show.

1. In the Supabase SQL editor, run `demo_1_books.sql`, then `demo_2_books.sql`, then `demo_3_activity.sql`.
2. To remove all of it later, run `demo_remove.sql`. It deletes the demo authors, and with them every demo story,
   chapter, choice and reading event.

Every book has a real premise, cast and a specific plot event for each chapter, and a hand-written opening chapter.
The rest of each chapter is assembled from that book's own atmosphere, character lines and hooks, so it reads as
plausible placeholder prose rather than finished fiction. The SQL is generated by `npm run demo:build` from the
story data in `scripts/demo/`. Demo authors use the reserved `.invalid` email domain and cannot sign in.

## Local development with a local Supabase

With Docker running: `npx supabase start` applies the migrations to a local stack and prints the API URL and anon
key for `.env.local`. Email confirmation is off locally, so sign-up logs straight in.

To open the local app from a phone or a preview link, set `NEXT_PUBLIC_SUPABASE_URL=/sb` and
`SUPABASE_INTERNAL_URL=http://127.0.0.1:54321`, rebuild, and run `npx next start -H 0.0.0.0`. The app then proxies
Supabase at `/sb`, so only the app's port needs to be reachable.

## What is in place

### Accounts: readers and writers

Everyone signs up with just an email (or Google) and gets a username; readers are known by it. Pen names are for
writers: the first time someone starts a story they can choose one (or keep writing under their username), and
change it later in settings. The database refuses a pen name on an account with no stories.

### Build step 10: moderation, polish, launch prep

- Report button on stories, author pages and comments (reason + optional details; one open report per person per
  item). Admins work through `/admin`: grouped by item, with dismiss, hide comment, take story down (with a note
  the writer sees) and restore.
- A taken-down story disappears from every list, page and chapter for everyone but its writer, who sees why. Only
  admins can change takedowns or hide comments; the database refuses it for anyone else.
- Admins choose which stories are featured for comic panels and their per-chapter limit.
- Mature stories stay out of lists unless the reader turns on "Show mature stories" in settings, and opening one
  shows an 18+ notice first (remembered on the device once confirmed).
- Rate limits on comments, reports, new stories, publishing and comic generation.
- Sitemap, robots.txt, share cards for the site and every story (cover-style image with title, author and blurb),
  canonical links; private pages are kept out of search engines.

### Build step 9: community and analytics

- Comments on chapters and on single paragraphs (tap a paragraph; paragraphs with comments show a count), with one
  level of replies, editing, deleting and an Author badge for the writer.
- Follow a story (new chapter alerts) or an author (alerts for all their stories); follower counts are public.
- Notifications: new chapters from followed stories and authors, replies, comments on your stories and new
  followers. The header bell shows the unread count.
- Writer analytics per story (Studio > Analytics): readers, chapter completion, returning readers, library adds,
  followers and comments over 7, 30 or 90 days; readers per day; readers and finishers per chapter with the biggest
  drop-off called out; Fresh Shelf and ranking status.

### Build step 8: comic panels

- For featured stories (rows in `comic_enabled_stories`, managed by admins), writers open **Comic panels** from the
  chapter editor. The chapter is split into 3 to 8 scenes, each with an editable caption and picture prompt.
- Five style presets (webtoon colour, manga ink, watercolour storybook, noir, painterly fantasy) and an optional
  reference image (stored privately) that guides every panel's look.
- Panels are generated one at a time or all at once. Every generation spends from a per-chapter cap (20 by default)
  enforced in the database; images can only be attached through the generation path, and nothing is shown to
  readers until the writer approves it. Approved images are stored, so each is generated and paid for once.
- Readers get a Text / Comic toggle on chapters with approved panels.
- Image provider: with `OPENAI_API_KEY` set (optionally `OPENAI_IMAGE_MODEL`, default `gpt-image-1`), panels come
  from the OpenAI Images API; without it, a built-in demo generator draws stylised panels at no cost.
- Migration `20261115000000_comics.sql`.

### Build step 7: choice points

- Writers add one choice per chapter from the chapter editor: put the cursor in a paragraph, choose "Add a choice
  after paragraph N", write the question and 2 or 3 options, each with its own short branch scene. The panel
  shows exactly where the choice appears and can move it to the cursor. Editing wording keeps existing picks.
- Readers meet the choice inline. The rest of the chapter appears once they pick (or skip). After picking they
  read their branch, see what share of readers chose each option, and can read the other paths; then the main
  story continues. The first pick is the one that counts. Signed-out readers can pick too.
- Authors can try their own choices without being counted, and see the totals. Chapters with a choice are tagged
  on the story page and in the studio.
- A chapter only counts as finished once the reader is past the choice. Picks made offline are kept on the device.
- Database functions `save_choice_point`, `choice_state` and `pick_choice` (migration
  `20261114000000_choice_points.sql`); clients cannot write picks directly.

### Build step 6: installable app and offline reading

- Installable on phones and desktops (web app manifest, Obsidian Quill icons including a maskable one, Apple
  touch icon). Chrome reports no installability errors.
- Service worker (`public/sw.js`, registered in production on HTTPS or localhost):
  - Downloaded stories (story page, every published chapter, cover) are kept until the reader removes them.
  - Recently visited reading pages (home, browse, stories, library, rankings) reopen offline; the newest 60 are
    kept. Hashed app files and fonts are cached as they load.
  - The writer studio and sign-in pages are never cached. Signing out deletes downloads and saved pages.
  - Online, pages always come from the network first, and downloaded copies refresh when visited.
- "Download for offline" on story pages, with progress, "Update offline copy (N new)" when chapters are added, and
  Remove. `/offline` lists downloaded stories and stands in for pages that are not saved; the library links to it.
- Offline, chapters open even if never visited, next/previous links work, and reading settings changed offline
  apply to saved chapters. Progress and reading events are sent again once back online.
- Offline features need HTTPS (or localhost); a phone opening the app over a plain `http://` LAN address gets the
  site without them.

### Build step 5: discovery

- Reading events: the reader logs opening a chapter and finishing it (the end of the text on screen after a
  believable time, re-checked by the server); a later visit logs a return; shelf adds and follows are logged by
  database triggers. Authors' own reads never count. Signed-out readers get a random `oq_aid` cookie and count
  for half. Clients cannot insert events directly; `log_reading_event()` validates and deduplicates them.
- Depth points per reader: each chapter finished (up to 10) 1, a return 2, a shelf add 3, a follow 2; opening
  alone 0, so readers who bounce lower a story's score. Depth is a smoothed average of points per reader.
- Fresh Shelf: every new story is shown to its first 75 distinct readers within 7 days. A view counts only when
  the row is on screen, and viewers see stories they have not been shown first. When the batch or the week ends
  the story graduates (depth at least 1.5) or stops being pushed; too few readers to judge gets one more week.
  Stories that stop being pushed stay in search and genre pages and can still rise if readers find them.
- Trending (past week, recent days weigh more) and Rising (under 90 days old, depth per reader) on the home page
  and `/rankings`, which also has Most finished and a genre filter. Writers see their Fresh Shelf status in the
  studio.
- `refresh_discovery()` recomputes scores every 15 minutes with `pg_cron`. Every threshold above lives in the
  one-row `discovery_settings` table, editable by admins.

### Build step 4: search, browse and home

- `/browse`: search titles, synopses, author names and tags (full-text plus typo-tolerant title matching), with
  filters for genre, status, length, last updated and sort, an "Include mature" switch, removable filter chips,
  pagination and popular tags. Empty form fields redirect to a clean URL.
- `/genre/[slug]` and `/tag/[slug]`: the same view locked to one genre or tag; story pages link to them.
- Home page rows: Continue Reading (signed in), Fresh Shelf (stories in their first week), Recently Updated, the
  four biggest genres, and a Browse by genre list.
- Mature stories are hidden from browse and home unless "Include mature" is ticked.
- Database functions `search_stories`, `popular_tags` and `genre_counts` (migration
  `20261112000000_search_browse.sql`), all running under the caller's Row Level Security.

### Build step 3: reader

- Story page (`/story/[id]`): cover, author, status, rating, word count and reading time, genres, tags,
  synopsis, published chapters, and Start reading / Continue: Chapter N.
- Chapter reader (`/story/[id]/chapter/[n]`) with a reading settings sheet:
  - Brightness (40 to 100 percent) that dims the whole screen.
  - Background: nine presets (Midnight, Charcoal, Slate, Night blue, White, Cream, Sepia, Parchment, Sage) or any
    custom colour; text colour is picked automatically for contrast (at least 7:1 on presets, 4.5:1 on any colour).
  - Background type: plain, paper grain or linen.
  - Fonts: Classic, Literata, Merriweather, Lora, EB Garamond, System sans, Inter, Atkinson Hyperlegible and
    OpenDyslexic (self-hosted via Fontsource).
  - Text size, line spacing and page width; reset to defaults.
  - Settings live in a cookie (and localStorage), so pages render in the chosen look with no flash.
- Reading progress bar, previous/next links and arrow-key navigation. Drafts and scheduled chapters return 404.
- Reading progress: the current chapter and scroll position are saved every few seconds and when the tab is
  hidden, and restored on any device signed into the same account.
- Library (`/library`): Reading, Plan to Read and Completed (a story sits on at most one of these), plus custom
  shelves you can create, rename and delete. Add to library from any story page; remove from a shelf in the
  library. Cards link straight to the chapter you are on.

### Build step 2: writer studio

- `/studio`: your stories with status, chapter count and published word count.
- `/studio/new` and the story page's "Story details": title, cover upload (JPG/PNG/WebP, 2 MB), synopsis,
  up to 3 genres, up to 15 tags (normalised, created on first use), content rating and status.
- Stories stay private drafts until "Publish story"; publishing starts the story's Fresh Shelf week.
- Chapter list with new chapter, move up/down, and delete (later chapters renumber).
- Chapter editor: distraction-free serif writing surface with a focus mode, live word count, autosave 1.5 s after
  typing (plus Ctrl/Cmd+S and on tab hide), a local backup offered back after a crash, retry when offline, and
  conflict detection so a stale tab never overwrites newer text.
- Publish now, schedule for a date and time, cancel a schedule, or unpublish. `pg_cron` publishes due chapters
  every minute, stamped with their scheduled time.
- Database functions `set_story_genres`, `set_story_tags`, `create_chapter`, `reorder_chapters`, `delete_chapter`
  and `publish_due_chapters` (migration `20261111000000_writer_studio.sql`); each checks story ownership.

### Build step 1: setup

- Next.js 15 + Tailwind v4 app with the dark Obsidian Quill theme, site header, home page shell.
- Supabase browser/server clients and a middleware that refreshes sessions and guards `/studio` and `/library`.
- Email/password and Google sign-in (`/login`), OAuth/email callback (`/auth/callback`), sign-out.
- Base schema for every table in the project scope, with Row Level Security:
  - Authors edit only their own stories, chapters, choice points and comic panels.
  - Readers edit only their own shelves, progress, follows, picks and comments.
  - Draft stories and unpublished chapters are visible only to their author.
  - Profiles cannot grant themselves admin; default shelves cannot be deleted.
- Triggers: a profile and the three default shelves on sign-up; chapter word counts; story word count and
  last-updated; a Fresh Shelf slot when a story is first published.
- Postgres full-text search on story title and synopsis, plus trigram title search.
- Storage buckets: `covers` (public), `references` (private), `comic-panels` (public; written server-side).
